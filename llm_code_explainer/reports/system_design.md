# 基于大模型的代码解释助手系统设计文档

## 1. 应用场景

本系统面向编程初学者、非计算机专业学生和刚开始接触 Python/C/C++ 的学习者。用户输入一段代码后，系统用中文解释代码的语言类型、主要功能、关键语句、变量含义、执行流程、潜在风险和学习建议，帮助用户降低阅读代码的门槛。

## 2. 系统目标

- 提供一个可直接运行的小型大模型应用系统原型。
- 默认使用 mock 模式，无需 API Key、无需网络即可演示。
- 可选支持 OpenAI API，用于展示真实大模型接口的接入方式。
- 提供不少于 20 条测试样例，并生成测试结果和评测报告。
- 保持代码量少、依赖少、结构清晰，符合课程作业级别而非生产级系统。

## 3. 系统架构

系统采用简单的分层结构：

```text
用户命令行输入
    ↓
app.py
    ↓
prompt_builder.py 构造提示词
    ↓
llm_client.py 统一模型接口
    ├── mock_llm.py 离线规则解释
    └── OpenAI API 可选真实调用
    ↓
中文结构化解释
```

批量评测流程：

```text
run_tests.py
    ↓
evaluator.py
    ↓
读取 data/test_cases.json
    ↓
调用 mock 模型生成解释
    ↓
生成 outputs/test_results.json 和 reports/evaluation_report.md
```

## 4. 输入输出设计

### 4.1 输入

系统支持两种输入方式：

- `--code`：直接在命令行中输入代码字符串。
- `--file`：从本地文件读取代码。

测试样例文件 `data/test_cases.json` 中每条样例包含：

- `id`：样例编号。
- `category`：样例类别。
- `language`：预期语言。
- `user_input`：用户输入代码。
- `expected_focus`：期望系统关注的知识点。
- `manual_score`：人工评分。

### 4.2 输出

系统输出中文结构化解释，栏目包括：

- 语言判断
- 功能概述
- 关键语句解释
- 变量说明
- 执行流程
- 潜在问题
- 优化建议
- 学习提示

这种固定结构便于老师验收，也便于对不同测试样例进行横向比较。

### 4.3 用户反馈设计

系统提供一个可选的轻量用户反馈机制。用户在命令行运行时可以传入：

```powershell
python app.py --code "print('hello')" --feedback-score 5 --feedback-comment "解释清楚"
```

系统会把反馈追加保存到 `outputs/feedback.jsonl`。每条记录包含反馈时间、评分、文字评价、代码片段预览和解释结果预览。该设计不使用数据库和登录系统，既能体现用户反馈机制，又保持课程作业原型的简洁性。

## 5. 模型调用方式

### 5.1 mock 模式

mock 模式是默认模式。系统通过 `code_analyzer.py` 对代码进行轻量静态分析，识别语言、行数、循环、条件、函数、类、输入输出、文件读写、排序、递归以及常见风险。然后 `mock_llm.py` 根据分析结果生成中文解释。

mock 模式特点：

- 不依赖网络。
- 不需要 API Key。
- 不需要第三方库。
- 输出稳定，适合课堂演示和作业验收。

### 5.2 OpenAI 模式

当环境变量 `LLM_MODE=openai` 时，`llm_client.py` 会尝试调用 OpenAI API：

- `OPENAI_API_KEY`：API Key。
- `OPENAI_MODEL`：模型名称，默认 `gpt-4o-mini`。

如果缺少 API Key、未安装 SDK 或调用失败，系统会返回友好错误信息，不会直接崩溃。

## 6. 异常处理机制

系统包含以下异常处理：

- 代码为空：提示用户代码内容不能为空。
- 文件不存在：提示文件路径错误。
- 文件路径不是普通文件：提示路径类型错误。
- `LLM_MODE` 非法：自动退回 mock 模式。
- OpenAI API Key 缺失：返回说明信息。
- OpenAI SDK 缺失：返回说明信息。
- OpenAI 调用失败：返回错误原因和改用 mock 模式的建议。
- 用户反馈参数非法：命令行参数解析会限制评分只能为 1 到 5。

系统不会执行用户输入的代码，只进行解释和静态分析，从设计上降低安全风险。

## 7. 系统特点

- 最小可运行：入口只有 `app.py` 和 `run_tests.py`。
- 依赖极少：默认只使用 Python 标准库。
- 离线可验收：mock 模式覆盖课程演示需求。
- 结构清晰：模型接口、提示词、静态分析和评测模块分离。
- 评测闭环完整：包含测试样例、输出结果、人工评分和报告。
- 包含结构化输出和轻量用户反馈机制，覆盖作业中的可选组件要求。

## 8. 局限性

- mock 模式是规则系统，不是真正理解代码的大模型。
- 对复杂算法、跨文件代码、库函数语义的解释能力有限。
- 递归识别和语言判断使用启发式规则，可能出现误判。
- 人工评分已经预置在测试样例中，不能完全代表真实用户满意度。

## 9. 改进方向

- 使用真实大模型提升复杂代码解释质量。
- 增加更多语言支持，例如 Java、JavaScript、Go。
- 将评测维度细化到每个输出栏目。
- 增加简单的 Web 页面，但仍保留 CLI 入口。
- 在不引入数据库的前提下，支持导出用户反馈表单。
